# ADR 0005: Propuesta de CI/CD (GitHub Actions y GHCR)

**Estado:** propuesto (la fase 1 ya está implementada)

## Pipeline
**CI (`.github/workflows/ci.yml`, en cada PR):**

| Job | Qué valida |
|---|---|
| backend | ruff (lint y formato), mypy strict, import-linter (capas hexagonales), pytest unitario y de API con Postgres y Redis como *service containers*, cobertura ≥ 80 %, `alembic check` |
| frontend | ESLint, `tsc --noEmit`, Vitest, `next build` |
| e2e | `docker compose up --build --wait` y Playwright: flujos por rol y el caso de dos pestañas del observador |
| security | gitleaks (secretos), pip-audit, npm audit, Trivy sobre las imágenes (HIGH/CRITICAL) |

**CD (`.github/workflows/cd.yml`):**
- **Push a `main`**: build con buildx y caché de GHA, push a **GHCR** con tags `sha`, `latest` y semver, más SBOM y provenance. Después, deploy automático a **staging**.
- **Tag `v*`**: deploy a **producción** a través del *environment* `production`, que tiene *required reviewers*, es decir, aprobación manual.
- **Deploy** (`infra/deploy/deploy.sh`): por SSH a una VM ejecuta `docker compose pull`, luego `migrate` y al final `up -d --wait`. Las migraciones van antes que la app.

## Roadmap propuesto
1. **Fase 1 (esta entrega):** CI completo, imágenes versionadas en GHCR, Dependabot y protección de rama (checks obligatorios).
2. **Fase 2:** staging y producción en una VM con Compose (ya scripteado), o en un PaaS de contenedores (Render, Fly.io, Railway, Azure Container Apps). Secretos en GitHub Environments. Conventional Commits con release-please para versionar y generar el changelog.
3. **Fase 3:** Kubernetes con Helm y Argo CD (GitOps), Terraform para la infraestructura, secretos en un gestor (Key Vault, Secrets Manager o Vault), observabilidad con OpenTelemetry, Grafana, Loki y Prometheus (los logs ya salen en JSON con `request_id`), y despliegues *blue/green* o *canary*.

## Por qué así
- Todo el pipeline se apoya en `docker compose` y en los mismos comandos del `Makefile`, así que se puede portar a GitLab CI o Azure DevOps sin reescribir la lógica.
- La misma imagen se promueve de staging a producción sin volver a construirla.
